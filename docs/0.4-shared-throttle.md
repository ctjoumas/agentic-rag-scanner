# Task 0.4 - Shared Throttle (`ISharedThrottle`)

> Phase 0 / Epic 0, story 0.4. Quick background for PR review.
> See also: `horizon-scanner-architecture.md` (Open considerations -> "Shared quota contention"),
> `implementation-plan.md` Phase 0, and `backlog.md` Epic 0 / 0.4.

## Why this exists
The scanner runs one agentic-RAG workflow **per topic group**. They originally ran sequentially and now
run **in parallel** (delivered in Epic 13 - see below). Every workflow hits the **same** shared services -
Azure OpenAI (TPM / RPM limits) and Bing (QPS limits) - so without a single shared gate, N concurrent
workflows would blow those quotas and trigger 429s.

`ISharedThrottle` is that single, injectable gate. All outbound, quota-limited calls funnel through
it, so we can cap how many / how often we hit OpenAI and Bing regardless of how many workflows are in
flight.

## Scope of THIS PR (Phase 0)
Only the **abstraction + a pass-through implementation**. There are **no real limits yet**, on
purpose:
- Phases 1-11 run sequentially, so contention isn't a problem yet.
- Wiring the interface now lets every call site be "throttle-ready" before we switch on real limits,
  with no later call-site churn.

The real limiter (built on `SemaphoreSlim` and/or `System.Threading.RateLimiting`, with per-service
TPM/RPM/QPS config) arrives in the hardening / parallelization phases. **Core stays package-free** -
the real implementation can wrap a `RateLimiter` without Core taking that dependency.

## The shape
```csharp
public interface ISharedThrottle
{
	// Waits until `permits` units of quota are free, then returns a lease. Dispose to release.
	ValueTask<IThrottleLease> AcquireAsync(int permits = 1, CancellationToken cancellationToken = default);
}

public interface IThrottleLease : IDisposable { }
```
- `permits` = 1 per request for RPM/QPS; pass an estimated token count for token-based limits (TPM).
- `NoOpThrottle` is the Phase 0 impl: `AcquireAsync` returns immediately and the lease's `Dispose`
  does nothing.

## The lease is a scope guard, not a parameter
The one non-obvious bit: the lease is **not passed into the LLM/Bing call**. It's a lifetime guard
(same idea as a lock). Throttling happens at the two ends - *acquire* (wait for room) and *dispose*
(release the slot); the call in between just runs.

```csharp
var lease = await throttle.AcquireAsync(ct);   // WAIT here if we're over the limit
try
{
	var resp = await chatClient.GetResponseAsync(...);   // the call doesn't know about the throttle
}
finally
{
	lease.Dispose();   // release the slot so the next waiter can proceed
}
```
Same pattern as `SemaphoreSlim.WaitAsync()` / `Release()`. Holding the lease = "I'm occupying a slot
of quota"; disposing it = "done, release it."

Dispose semantics: for **concurrency** limits it returns the slot (essential); for **time-based**
limits (RPM/QPS/TPM) permits refill on a timer, so dispose is a no-op there - but callers always
`using` it so the same code works for both.

## How to use it (everyday)
Prefer the `ExecuteAsync` extension - it does acquire/run/release for you, so call sites never touch a
lease:
```csharp
var resp = await _throttle.ExecuteAsync(
	ct => _chatClient.GetResponseAsync(prompt, ct),
	cancellationToken: token);
```
Drop down to `AcquireAsync` only if you need to hold a slot across something `ExecuteAsync` can't
express (e.g. a streamed response).

## Epic 13 - real throttle + parallel fan-out (13.1 / 13.2 / 13.3)

The `NoOpThrottle` is replaced by **`RateLimitingThrottle`** (Core), and the orchestrator now runs
topic groups **in parallel**. Two *separate* limits apply - keeping them separate is deliberate:

| Dimension | What it caps | Where it lives | Config (`Throttle` section) |
| --- | --- | --- | --- |
| **Group parallelism** | How many topic-group workflows run at once in a single scan | `ScanOrchestrator` (a `SemaphoreSlim` worker gate) | `MaxParallelTopicGroups` |
| **Call concurrency** | Outbound Azure OpenAI / Bing calls in flight at once across all groups | `RateLimitingThrottle` (a `ConcurrencyLimiter`) | `MaxConcurrentCalls` (default 8) |
| **Request budget (RPM/QPS)** | Outbound calls per rolling window, replenished smoothly | `RateLimitingThrottle` (a `TokenBucketRateLimiter`) | `RequestsPerWindow` (**default 0 = disabled**) / `WindowSeconds` |
| **Backpressure queue** | Callers allowed to wait once a limit is hit (else `ThrottleRejectedException`) | `RateLimitingThrottle` | `QueueLimit` |

> **Why two layers (and not one).** A single shared concurrency limiter used for *both* the whole group
> and its inner calls **deadlocks**: a group would hold a slot for its entire lifetime while the very
> calls it needs wait for a slot from the same limiter. So the group cap is a distinct `SemaphoreSlim` in
> the orchestrator, and `ISharedThrottle` gates only individual outbound calls. `WorkflowTopicGroupExecutor`
> therefore does **not** wrap the whole workflow in the throttle - per-call throttling happens inside
> `ResilientChatClient` / `WebSearchAgent`.

### Tuning under parallel load (story 13.3)
Goal: stay within Azure OpenAI **TPM/RPM** and Bing **QPS** with *N* groups in flight.

1. **Start from the deployment's real limits.** Read the model deployment's RPM (and TPM) from the
   Foundry/Azure OpenAI quota, and the Bing tier's QPS. These are the ceilings.
2. **`RequestsPerWindow` defaults to 0 (RPM disabled) - concurrency-only.** There is no safe universal
   RPM: a value below the deployment's real quota would needlessly stall scans (calls queue waiting for
   token replenishment). Only set it once you know the quota, e.g. RPM 60 -> `RequestsPerWindow: 60`,
   `WindowSeconds: 60`, leaving headroom for retries. The budget is replenished **smoothly** across the
   window (not one big refill), so there is no per-window "cliff".
3. **Set `MaxConcurrentCalls`** to the service's concurrent-connection comfort level (default 8). This is
   the hard cap on simultaneous outbound calls no matter how many groups run.
4. **Set `MaxParallelTopicGroups`** to the fan-out width you want (default 4). More groups in flight
   improves throughput only until `MaxConcurrentCalls` / `RequestsPerWindow` become the bottleneck - past
   that, extra groups just queue on the throttle.
5. **`QueueLimit`** is the backpressure allowance: waiters beyond it get `ThrottleRejectedException`, which
   is classified transient so the caller's Polly pipeline backs off (honoring `Retry-After`) and retries.
   Keep it generous (default 256) so short bursts wait instead of failing.

Rule of thumb: `MaxParallelTopicGroups x (typical concurrent calls per group)` should not exceed
`MaxConcurrentCalls`, and sustained call rate should not exceed `RequestsPerWindow / WindowSeconds`.

### Observability (story 13.2)
`ScannerDiagnostics` exposes an OpenTelemetry `ActivitySource` + `Meter` (registered via
`AddScannerObservability`). Traces + metrics are exported to Azure Monitor when an App Insights
connection string is set; when none is set (typical local dev) the instruments are still collected but
not exported anywhere - there is deliberately **no console exporter** (it would flood the terminal and
bury the Serilog logs). Logs stay on the existing Serilog -> App Insights sink, so OpenTelemetry here
carries only traces + metrics and does not double-emit logs:
- **`scanner.topic_groups.in_flight`** (gauge) - groups executing in parallel right now.
- **`scanner.topic_group.worker_wait`** (histogram, ms) - time a group queued for a worker slot; a rising
  value is the signal that `MaxParallelTopicGroups` is saturated (backpressure).
- **`scanner.topic_groups.completed`** (counter, tagged by status) - Completed vs Failed groups.
- **`topic_group.execute`** spans - one per group, tagged `scanner.run_id` / `scanner.topic_group_id`, so
  concurrent groups appear as parallel traces.

Per-group start/finish + gate-wait are also logged (Serilog -> App Insights) scoped by
`runId`/`topicGroupId` for correlation.
